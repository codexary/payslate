# ADR 0013：拒绝重叠班次并明确重复上传的处理方式

Ravi Menon — 2026-07-29

## 状态

2026-07-29 采纳。

## 背景

[ADR 0012](0012-timesheet-upload-limits.zh-CN.md) 的最后一段留下了一个尚未解决的计薪缺陷：同一文件上传两次，就会为其中的班次支付两次工资；同一员工的班次即使时间重叠，也会被接受。产品负责人 Margaret O'Connell 已将修复这一缺陷列为优先事项。

实际使用中，网络超时就可能触发重复上传。薪资操作员的客户端会重试，而第一次请求此时可能仍在处理。如果只是先查询、再插入，两次请求都可能查不到已有班次，随后各自插入相同的班次，导致重复计薪。

## 决定

班次时间采用左闭右开的区间 [start, end)，即包含开始时刻，不包含结束时刻。对于同一员工，只要两个班次各自的开始时间都早于另一个班次的结束时间，就视为重叠。前一个班次恰好在后一个班次开始时结束，两者首尾相接，不算重叠。

上传时拒绝重叠班次，指出出错的行号，但绝不回显原始行内容。同一文件内的班次重叠属于客户端输入错误，返回 400；与已存储班次重叠则属于与现有数据冲突，返回 409。

先确定每行数据对应的员工，再在本次上传的事务内锁定这些员工记录，然后才检查是否与已存储班次重叠并插入新班次。加锁使用以下语句：

```sql
SELECT id FROM employees WHERE employer_id = ? AND id IN (...) ORDER BY id FOR UPDATE
```

这样，同时上传同一员工的班次时，后续请求必须等待，避免两个请求同时通过检查。这一做法在使用 H2 的构建和 PostgreSQL 上均可使用。网络超时后重传同一文件，只要第一次上传已经提交，重传就会返回 409 并指出行号，薪资操作员也由此得知该文件已经导入。如果第一次请求仍在处理，重试请求会等其事务结束后再检查已存储的班次。

暂不引入用于上传内容去重的幂等键。这需要先确定一个能稳定标识一次上传的业务键，并建立去重记录存储；目前拒绝重叠班次已经能够防止重复计薪。如果部分重传变得常见，例如部分班次已导入后，再上传一个既含已导入班次、又增加了不重叠的新班次的文件，则应重新评估幂等键方案。

## 考虑过的其他方案

- 使用 PostgreSQL 的 `btree_gist`，对雇主、员工和时间范围（tsrange）设置排他约束：不作为主要保障，因为默认构建使用 H2，而 H2 没有这种约束，无法在该环境中落实同一规则。
- 现在就引入用于上传内容去重的幂等键：暂缓。这需要稳定的上传业务键和去重记录存储，而拒绝重叠班次已能防止重复计薪。如果部分重传变得常见，再重新考虑。
- 只在应用中检查，不锁定员工记录：不采用。网络超时引发重试时，两个并发请求仍可能同时通过检查，随后插入重复班次。

## 后果

拒绝新的重叠班次并不能追回修复前已经多付的工资。团队可运行以下查询，找出已有的重叠班次，再与 Margaret 单独核对并处理多付的工资：

```sql
SELECT a.employer_id, a.employee_id, a.id AS shift_a, b.id AS shift_b
FROM timesheets a
JOIN timesheets b
  ON a.employer_id = b.employer_id AND a.employee_id = b.employee_id
 AND a.id < b.id AND a.starts < b.ends AND b.starts < a.ends
ORDER BY a.employer_id, a.employee_id, a.id;
```

员工行锁会让同一员工的并发上传短暂排队、依次处理。这种短时间的锁等待对薪资业务可以接受；加锁是为了保证计薪正确，并非为了提高吞吐量。
