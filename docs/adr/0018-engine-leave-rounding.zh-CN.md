# ADR 0018：冻结引擎只作已付金额的差分 oracle

Ravi Menon — 2026-08-25

## 状态

2026-08-25 通过。

## 背景

`DifferentialEngineFuzzTest` 把冻结的 2004 引擎和重构后的 `PayEngine` 喂同一份排班，比较两者的输出。应发、税、实发、养老金这几笔钱，两套引擎都从精确的整数分钟算出，所以一致。差别在于喂给工时显示和年假累计的那个普通工时总数怎么存：冻结引擎用一个 `double`，每过一个普通分钟就加一次 `1.0/60.0`；`PayEngine` 则直接拿精确的整数分钟去除。

在一个月的排班里，模糊器找到一份排班：钱分文不差，年假却差 0.0001 小时。把普通分钟总数从 1 走到 12000，按两套引擎各自的算法舍入（一边是 `double` 累加，一边是精确除法取到十位），各自乘上 `0.076923` 的累计率、再 HALF_EVEN 到四位，年假会在恰好四个总数上分开：

| 普通分钟 | 冻结（double） | 重构（精确） |
| --- | --- | --- |
| 3000 | 3.8461 | 3.8462 |
| 7000 | 8.9743 | 8.9744 |
| 9000 | 11.5385 | 11.5384 |
| 11000 | 14.1026 | 14.1025 |

在 3000 分钟处，`double` 累加出来是 49.999999999998444，比精确的 50 差了一丝，于是冻结那边的年假往下舍。但这个差没有固定方向：到 9000 和 11000 分钟，反而是 `double` 那边更大。差距永远是第四位上的一个单位（0.0001 小时）。工时显示舍到四位时看不出来——3000 分钟处两边都是 50.0000——因为只有年假会把这个总数乘上累计率，落到另一个 HALF_EVEN 的分界上。

## 决定

重构后的 `PayEngine` 对它产出的每一个值都为准，工时显示和年假也在内。冻结引擎只留作已付金额——应发、税、实发、养老金——的差分 oracle，不作工时显示和年假的 oracle。于是差分测试比较已付金额和工资单的不变式，另一个回归把上面那份排班上两边各自的年假钉住，让它不会悄悄漂走。

薪酬规则是年假按普通工时累计；精确的整数算法才是这条规则的正确实现，显示值在几个特定总数上差 0.0001 小时，是冻结引擎的一个舍入残留，而不是哪一套引擎要去修的缺陷。Margaret 认可以精确的一边为准。

## 考虑过的其他做法

- **把冻结引擎改成精确累加。** 否决。冻结引擎是迁移的基线，一字不改地留作被替换的那套系统，动它就失去了拿它作对照的意义。
- **在 `PayEngine` 里把 `double` 累加加回来，好让两边一致。** 否决。那是拿一个正确的精确结果去换一份浮点误差的复刻。
- **任何分歧，连年假也算，都当发布阻断项。** 否决。钱是对的、也相等；为四个总数上 0.0001 小时的显示差异卡住迁移，对薪酬没有任何后果。
- **把 oracle 收窄到已付金额，并把年假差异记下来（选定）。** 既守住了真正要紧的迁移保证——钱分文不差——又把这处已知的显示差异写在评审看得见的地方。

## 后果

- 差分 oracle 不再比较工时显示和年假；它比较已付金额和不变式（实发 = 应发 − 税 − 扣款；应发与税不为负）。
- `LeaveRoundingDifferenceTest` 记下两套引擎在那份排班上的年假，日后任一舍入路径一改，就会测试失败，而不是无声通过。
- 这个 oracle 抓不到两套引擎共有的错（比如共用的预扣税表里写错一行），不变式也判断不了税额本身对不对。那些由税表证明和边界测试守着，不在这里。
