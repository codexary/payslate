# ADR 0015：要求桌面导出带控制尾记录

Ravi Menon — 2026-08-10

## 状态

2026-08-10 采纳。

## 背景

`aba-convert` 把桌面版的批次导出转成银行的 ABA 版式。为外部评估做准备时，Kwame 发现一份在行边界截断的导出——复制或传输中途停了——会被照常转换：剩下的记录拼出一份自洽的 ABA 文件，于是有一名员工被悄无声息地漏发了。截在记录中间的导出会报错退出，但此时已经把 ABA 头记录写到了标准输出，留下半份文件。Java 的 `AbaFile.parse` 早就用尾记录核对记录条数和合计，继承来的 C 转换器却从来没有。

## 决定

桌面导出必须以一行控制尾记录结束：一个 `T`、6 位记录条数、10 位以分为单位的合计，之后除了行尾不能有别的内容。`aba-convert` 先把整份输入读一遍、把解析好的记录存在内存里，只有在表头存在、记录条数等于明细行数、声明合计等于各笔金额之和、且尾记录之后没有数据时，才写输出。任何对不上——包括缺少尾记录或尾记录带多余字符——都以状态 2 退出、不写任何输出。

空批次——尾记录声明零条记录、合计为零、没有明细行——被拒绝而不是转换。一份没有付款的银行文件没有意义，几乎总意味着导出出了错；Kwame 确认桌面产品不会有意产生这样的文件。

控制尾记录由桌面产品 Payslate 7 写出。较旧的桌面版本不写它，其导出此后被拒绝，并提示从打过补丁的 Payslate 7 重新导出。该补丁随评估前发布的 Payslate 7 维护版一起发货；操作员装上之前，该站点无法转换新的导出。桌面版的发布和时间由 Kwame 负责；碰到拒绝的操作员，Chloe 的团队已备好提示文案和重新导出的步骤。

## 考虑过的其他方案

- 在头记录里声明记录条数和合计，而不是尾记录：不采用。头记录里的条数同样能查出少了记录，但桌面产品是边写边算的，条数和合计要写完最后一笔才知道，放在文件末尾最自然。尾记录也与 ABA 格式本身以及 Java 侧 `AbaFile.parse` 的做法一致。
- 缺尾记录只警告、仍然转换：不采用。悄无声息地少发工资正是这次改动要堵住的失败；批处理作业上的一条警告很容易被忽略。
- 逐行校验和：不采用，超出这个格式的需要。记录条数加合计已能抓住截断和金额篡改，也与 Java 侧已有的核对口径一致。

## 后果

用着未打补丁桌面版的操作员在升级之前无法转换；拒绝消息和 Chloe 的步骤把升级路径讲清楚。能对得上的尾记录并不能对银行传输做认证——能同时改写记录和尾记录的攻击者照样能过——所以经认证的传输在威胁模型里仍然开着。
